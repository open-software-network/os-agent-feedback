## Environment variables

| Variable | Required | Purpose |
| --- | --- | --- |
| `EPODE_API_KEY` | Yes | Server-side product key for enrichment, context, decisions, and outcomes |
| `EPODE_API_URL` | No | Override the Epode origin for local/canary testing only |
| `AGENT_FEEDBACK_KEY` | Legacy | Temporary compatibility name for the same server-side product key |
| `AGENT_FEEDBACK_MODE` | No | `never_ask` (default), `ask_once`, `ask_always`, or `off` |
| `AGENT_FEEDBACK_ENABLED` | No | Set to `false` for the emergency kill switch |
| `AGENT_FEEDBACK_URL` | No | Override the Epode origin for local/canary testing only |

Do not use `AGENT_FEEDBACK_READ_KEY` in a product integration. Read keys are for the optional Epode dashboard MCP
client and cannot sign feedback capabilities.

## Customer enrichment options

| Option | Purpose |
| --- | --- |
| `include` | Explicit company routes or tools eligible for a context request |
| `authenticate` | Express/Fastify product authentication for included business routes; exact capability relay paths bypass it |
| `purpose` | `product_personalization` or `targeted_advertising` |
| `identify` | Returns verified `accountRef`/`userRef`, product-owned `anonymousRef`, or nothing for ephemeral use |
| `remember` | Requests permission to retain useful context; stable identities default to true |
| `shouldRequest` | Optional product-owned outcome boundary; errors preserve the original response |
| `shouldRequestHtml` | Optional HTML-specific outcome boundary |
| `maxHtmlBytes` | Largest server-rendered HTML string eligible for injection (default 512 KiB) |
| `timeoutMs` | Enrichment and company-context timeout (default 250 ms); selected responses wait up to this bound and fail open |
| `relayTimeoutMs` | Same-origin consent/answer relay timeout (default 5 seconds); retryable outages return `503` |

The Node HTTP adapters automatically reserve and mount the company-owned enrichment relay at `/_epode/v1/enrichment/consent` and
`/_epode/v1/enrichment/answers`. Do not implement application behavior on those paths.

## Legacy feedback mode alignment

The SDK signs the initial feedback action locally so Epode never sits on the product response path.
`feedbackMode` / `AGENT_FEEDBACK_MODE` therefore controls the question or report action agents see.
The dashboard policy independently enforces what consent and reports Epode will accept.

Keep both values aligned. After changing the dashboard policy, update `AGENT_FEEDBACK_MODE` in the
product and redeploy it; Setup shows the exact current value. Until that deploy finishes, the backend
fails closed when an older product action conflicts with the new policy, but agents may still see the
old instruction. The envelope's `configuredMode` helps diagnose this drift.

## Common adapter options

| Option | Purpose |
| --- | --- |
| `apiKey` / `api_key` | Product key, normally read from the environment |
| `include` | Route patterns that receive feedback contracts |
| `feedbackMode` / `feedback_mode` | Explicit mode override |
| `accountRef` / `account_ref` | Stable opaque account, tenant, or workspace ID from verified product authentication |
| `userRef` / `user_ref` | Stable opaque user ID from verified product authentication |
| `anonymousRef` / `anonymous_ref` | Stable product-owned first-party pre-login visitor ID |
| `customerRef` / `customer_ref` | Durable Ask once compatibility subject; when `accountRef` is present, use the exact same account ID |
| `sessionRef` / `session_ref` | Optional server/product-proven journey reference; omit it rather than infer continuity |
| `consentTimeoutMs` / `consent_timeout` / `AGENT_FEEDBACK_CONSENT_TIMEOUT_MS` | Timeout for optional consent-cache warming or protocol-specific lookups (default 750 ms). HTTP product responses never await it. |
| `endpoint` | Override Epode origin in tests |

Never use names, emails, prompts, raw caller inputs, agent/tool arguments, or unverified token claims. Do not pair
`customerRef` with `userRef` alone or with a different `accountRef`. Identity and journey accessors add private,
nonblocking telemetry context; they never add those references to the agent-facing feedback envelope.

## Route patterns

Configure routes in code so configuration is reviewed and deployed with the product. Use exact paths for narrow
surfaces and framework-supported wildcards for related routes. Do not instrument the entire application unless all
successful responses are intended for customer agents.

## Key rotation

Rotate a key from Setup. The previous key remains valid for one hour so you can deploy the replacement without
dropping product traffic. Put the new value directly into the deployment secret manager and keep it out of browser
storage, shell history, CI logs, repositories, MCP clients, and product-auth requests. Consent is product-scoped, so
rotating a key does not expose or change the raw customer reference.
